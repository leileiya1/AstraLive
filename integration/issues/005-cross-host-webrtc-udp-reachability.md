# ISSUE-005: Cross-host WebRTC UDP reachability

Status: **CLOSED — RESOLVED BY DEPLOYMENT ICE CONFIGURATION** on 2026-10-07. Category: STUN/ICE deployment. Discovered during RTX 2060 GPU Acceptance on 2026-10-06.

Mac Chrome completed non-trickle SDP signaling through Go to the Ubuntu RTX 2060 Runtime. With the current default `new RTCPeerConnection()` configuration, the browser reported both tracks but ICE remained `checking` and the connection remained `connecting` after 10 seconds. A Mac aiortc peer using the same public Go endpoint did connect.

The Chrome offer carried mDNS host candidates in the default run. A diagnostic run with local-IP masking disabled exposed only the Mac's `198.18.0.1` and `fdfe:dcba:9876::1` host candidates. The Runtime answer included `10.65.13.94`, Docker/CNI interfaces, IPv6 addresses, and server-reflexive candidates (`162.128.207.75` and `95.40.15.153` observed in SDP; external reachability was not independently verified). The Runtime host's private address is `10.65.13.94`; the Mac's private address is `10.65.3.44`. A direct UDP probe from the Mac to a temporary listener bound on Ubuntu `10.65.13.94:39047` timed out on both ends. SSH/TCP signaling worked. Ubuntu firewall status could not be read without sudo; the specific block point remains unconfirmed.

Adding `stun:stun.l.google.com:19302` **only to the test browser's peer configuration** made the initial diagnostic connect, without disabling mDNS. That run observed 24 new inbound audio packets, positive audio energy (`1.574e-8`) and 12 new decoded video frames.

The production `useLivePreview()` now reads build-time `VITE_WEBRTC_*` settings from `frontend/src/config/webrtc.ts` and passes `RTCConfiguration` to `RTCPeerConnection`. A normal AstraLive frontend build with `VITE_WEBRTC_STUN_URLS=stun:stun.l.google.com:19302` connected Mac Chrome to Ubuntu Runtime through the public Go SDP endpoint. No STUN value was injected into the browser test peer. The Chrome test only wrapped the constructor to observe the configuration and stats. A quiet, non-muted preflight and the subsequent 30-minute run showed increasing positive audio energy and decoded video. [Quiet preflight](../evidence/browser-preflight-quiet-45s-media.json) and [30-minute browser media](../evidence/browser-connected-soak-30m.json).

Acceptance impact: cross-host **ICE reachability PASS** with the formally configured frontend STUN build; this resolves ISSUE-005. A later 30-minute run kept ICE and `connectionState` connected for 1,826 seconds, with positive and increasing audio energy and decoded video throughout 60 regular samples and all 52 Runtime cycles. [30-minute browser evidence](../evidence/browser-connected-soak-30m.json) and [audit](../evidence/browser-connected-audit-30m.json). No TURN relay was needed on this Mac ↔ Ubuntu path. STUN is not sufficient for every network.

Deployment follow-up: configure an appropriate STUN server in the frontend build for this network. Use TURN where host/server-reflexive candidates cannot traverse NAT or UDP policy. Keep Contract v1.1.0 unchanged; browser media remains direct Browser ↔ Runtime, with Go forwarding SDP only. The 30-minute browser-connected gate passed separately; the one-hour soak remains a later gate.
